# 移植到 QGIS 插件 —— 可行性验证报告

> 目标：把 DGIS（Tauri 桌面端）的核心能力移植为 **QGIS 插件**，一套代码跨 macOS / Windows 使用。
> 核心功能四项：**内置三种图源 · 5 km 半径覆盖圆（可复制、可随意拖动）· 线测量 · 面积测量**。
> 用途：机场（大疆机场 / DJI Dock）覆盖区范围选择，实测有效覆盖半径 **5 km**。

## 结论（先说结果）

**可行，且工作量比预期小。** 四项核心功能全部通过**真机实测**（不是纸面推演）：
三项可直接复用 QGIS 原生能力，只有「5 km 圆的精确生成」需要自己实现，而正确做法已验证为
**以圆心为中心的方位等距投影（aeqd）**，半径误差 **0.000 m**。

同时验证出一个**必须规避的坑**：拖动圆时若直接平移几何，跨纬度拖会严重变形（实测偏差最大 **989.76 m / 19.8%**），
必须「按新圆心重建」或把图层放在投影坐标系下。详见 §3.3。

## 2. 四项核心功能逐项验证

### 2.1 内置三种图源 —— ✅ 通过

三个图源沿用 DGIS 现有配置，用 QGIS 标准的 `type=xyz` 方式构造栅格图层：

```python
uri = f"type=xyz&url={url}&zmin=0&zmax=18"
lyr = QgsRasterLayer(uri, name, "wms")
```

| 图源 | 瓦片顺序 | QGIS `isValid()` | CRS | 瓦片实测（HTTP） |
| --- | --- | --- | --- | --- |
| Esri World Imagery | `{z}/{y}/{x}` | **True** | EPSG:3857 | 200，18,138 bytes，image/jpeg |
| GEOVIS Earth 影像 | `{z}/{x}/{y}` | **True** | EPSG:3857 | 200，12,132 bytes，image/webp |
| 四维地球 2024 卫星影像 | `{z}/{y}/{x}` | **True** | EPSG:3857 | 200，7,464 bytes |

provider 为 `wms`，覆盖范围 `-20037508.34 … 20037508.34`（全球 Web Mercator）。
**结论：三个图源在 QGIS 里开箱可用，无需任何适配。**

> 实测踩坑：`QgsApplication.setPrefixPath()` 必须传 **`/Applications/QGIS.app`**（而非 `…/Contents/MacOS`），
> 否则只注册到 16 个 provider、没有 `wms`，图层一律报 "Cannot instantiate the 'wms' data provider"。
> 传对后注册 33 个 provider（含 `wms`/`gdal`/`ogr`/`WFS`/`postgres` 等）。

### 2.2 5 km 半径覆盖圆 —— ✅ 通过（但只有一种做法正确）

这是**唯一需要自己写算法**的部分。以圆心 (116.40, 39.90) 生成 r=5 km、72 段的圆，
用测地线正算（`computeSpheroidProject`）作真值基准，实测各方案圆周顶点到圆心的椭球距离：

| 方案 | 半径范围 | 最大偏差 | 结论 |
| --- | --- | --- | --- |
| A. 在 EPSG:4326 上直接 `buffer(5000/111320)` 度 | 3841.10 ~ 4987.12 m | **1158.90 m（23.18%）** | ❌ 完全不可用 |
| B. 转 UTM 50N 后 `buffer(5000)` 再转回 | 5001.82 ~ 5001.85 m | 1.85 m（0.037%） | ⚠️ 可用，但跨带需换带 |
| **C. 以圆心为中心建 aeqd 投影后 `buffer(5000)`** | **5000.000 ~ 5000.000 m** | **0.000 m（0.000%）** | ✅ **采用** |

**采用方案 C**：`+proj=aeqd +lat_0={lat} +lon_0={lon} +datum=WGS84 +units=m +no_defs`
（方位等距投影：从圆心出发的距离与方位角都保真，所以 5 km 圆是严格的测地线圆，且与 UTM 分带无关）。

配套验证：

| 指标 | 实测 | 理论值 |
| --- | --- | --- |
| 单圆覆盖面积 | **78.5336 km²** | πr² = 78.5398 km²（差 0.008%） |
| 覆盖圆周长 | **31.4153 km** | 2πr = 31.4159 km |

**投影无关性**：圆生成在 EPSG:4326 后再转到 3857 / UTM 50N / CGCS2000 3°带(EPSG:4545)，
半径偏差分别为 1.63 / 0.02 / 0.22 m —— 均可忽略，说明**用户工程用什么坐标系都不影响精度**。

### 2.3 可复制、可随意拖动 —— ⚠️ 通过，但实现方式有讲究

这是本次验证**最重要的发现**。「拖动」有两种实现，差别巨大：

| 拖动场景 | ① 直接平移几何（QGIS 原生"移动要素"的行为） | ② 按新圆心重建圆 |
| --- | --- | --- |
| 同纬度平移 2° 经度 | 5000.0 ~ 5000.0 m（偏差 0.00 m） | 0.000 m |
| 北京 → 上海（39.9N→31.2N） | 4992.8 ~ **5572.2** m（偏差 **572.16 m / 11.44%**） | **0.000 m** |
| 北京 → 广州（39.9N→23.1N） | 4987.1 ~ **5989.8** m（偏差 **989.76 m / 19.80%**） | **0.000 m** |
| 北京 → 哈尔滨（39.9N→45.8N） | 4545.3 ~ 5005.2 m（偏差 **454.66 m / 9.09%**） | **0.000 m** |

**原因**：EPSG:4326 下经度 1° 的实地长度随纬度变小，整体平移会把正圆压成椭圆。

**对策（三选一，推荐第 1 条）**：
1. 插件自实现拖动工具：鼠标移动时**按新圆心重建圆**（aeqd），半径恒为 5 km —— 实测偏差 0.000 m；
2. 覆盖圆图层改用**投影坐标系**（如 CGCS2000 3°带 / UTM），此时原生平移工具即可，无需自实现；
3. 若坚持用 QGIS 原生移动工具 + 4326 图层，则必须标注「跨纬度拖动后需重算半径」。

**性能（自实现重建的开销完全够用）**：

| 操作 | 实测 |
| --- | --- |
| 创建 100 个 5 km 圆 | 268.5 ms（单个 **2.68 ms**） |
| 连续拖动 100 个圆（每个都重建几何） | 273.9 ms（单次 **2.74 ms**） |

60 fps 一帧预算 16.7 ms，单次重建 2.74 ms —— **拖动时同时重建几十个圆也不掉帧**。

**复制**：QGIS 在编辑模式下原生支持要素复制粘贴；插件可再做「复制到点击位置」并复用同一套
`circle(new_lon, new_lat)` 生成逻辑，实测副本面积仍为 **78.5336 km²**，半径不失真。

### 2.4 测量工具（线测量 / 面积测量）—— ✅ 通过

`QgsDistanceArea` 一行配置即可椭球测量，不用自己写大地主题解算：

```python
da = QgsDistanceArea()
da.setSourceCrs(QgsCoordinateReferenceSystem("EPSG:4326"), QgsProject.instance().transformContext())
da.setEllipsoid("EPSG:7030")          # WGS84 椭球，测地线
da.measureLine([p1, p2, p3])          # 线测量，返回米
da.measureArea(geometry)              # 面积测量，返回平方米
da.measurePerimeter(geometry)         # 周长
```

| 验证项 | 实测 | 参考 |
| --- | --- | --- |
| 线测量 北京→上海 | **1069.819 km** | 大圆距离约 1067~1070 km ✅ |
| 4 点折线分段累计 | 1135.150 km | 与 `measureLine(折线)` 一致 ✅ |
| 面积测量 5 km 圆 | **78.5336 km²** | πr² = 78.5398 km² ✅ |
| 面积测量 1°×1° 方格（39~40°N） | **9549.5 km²** | 111320·cos39.5°×110900 ≈ 9530 km² ✅ |

> 对照组：若不设椭球（`setEllipsoid("NONE")`），北京→上海返回的是 **10.1**（把度当笛卡尔），毫无意义。
> 所以插件里**必须显式设椭球**，这是线/面积测量正确的前提。

### 2.5 补充验证：圆图层"跟工程 CRS 一致"时的精度（重要）

用户决策：**圆图层的坐标系与 QGIS 工程一致，工程无空间参考则用 WGS84**。
据此实测「**在该 CRS 下直接 `buffer(5000)`**」的效果（圆心北京 116.40,39.90，转回 WGS84 椭球量测）：

| 工程 / 图层 CRS | 实测半径 | 误差 | 结论 |
| --- | --- | --- | --- |
| EPSG:4326 WGS84 地理 | — | buffer 单位是**度**，5000 度无意义；若换算成 0.0449° 则误差 1158.90 m（23.18%） | ❌ 不能直接 buffer |
| EPSG:4490 CGCS2000 地理 | — | 同上 | ❌ 不能直接 buffer |
| **EPSG:3857 Web Mercator** | 3825 ~ 3841 m | **1175.01 m（23.50%）** | ❌ **不可用** |
| EPSG:32650 UTM 50N | 5001.8 ~ 5001.9 m | 1.85 m（0.04%） | ✅ 可用 |
| CGCS2000 高斯 3° 带（中央 117°E） | 4999.8 ~ 4999.9 m | **0.18 m（0.00%）** | ✅ 可用 |
| Albers 等积圆锥（中国） | 4916 ~ 5085 m | 85.36 m（1.71%） | ⚠️ 等积投影不保距离 |

**Web Mercator 的误差随纬度急剧恶化**（同一做法换城市）：

| 城市 | 误差 | 实际半径 |
| --- | --- | --- |
| 三亚 18.2°N | 277.88 m（5.56%） | 约 4722 m |
| 广州 23.1°N | 425.30 m（8.51%） | 约 4575 m |
| 北京 39.9°N | **1175.01 m（23.50%）** | 约 3825 m |
| 哈尔滨 45.8°N | **1520.53 m（30.41%）** | 约 3479 m |
| 漠河 52.6°N | **1965.17 m（39.30%）** | 约 3035 m |

> **这是个真实且高发陷阱**：添加 XYZ 底图（EPSG:3857）时 QGIS 会询问 / 自动把工程 CRS 改成 3857。
> 一旦工程变 3857，"在工程 CRS 里 buffer(5000)" 得到的覆盖圈在哈尔滨会缩水到 3.5 km。

**拖动（在图层 CRS 下直接平移几何）同样受影响**：

| 图层 CRS | 北京→广州 | 同纬度东移 2° |
| --- | --- | --- |
| UTM 50N | 6.99 m | 1.15 m |
| CGCS2000 高斯 3° 带 | 8.98 m | 0.92 m |
| Web Mercator | **425.30 m** | **1175.01 m** |

### 2.6 由此确定的实现口径（对用户决策的精确落实）

「跟工程 CRS 一致」应理解为**存储与显示一致**，**不是"在工程 CRS 里做 buffer"**：

```
圆心(工程CRS) --转--> WGS84 经纬度
      --> 以该经纬度为中心建 aeqd 投影  --> buffer(5000 m)   ← 测地线圆，精确 5 km
      --> 转回工程 CRS --> 写入图层                          ← 图层 CRS = 工程 CRS ✅
```

- **生成**：一律走 aeqd 测地线；**存储**：一律转到工程 CRS。这样工程用 4326 / 3857 / UTM / 高斯
  都能得到精确 5 km（§2.2 已实测：转到 3857 / UTM / CGCS2000 偏差分别 1.63 / 0.02 / 0.22 m）。
- **拖动**：同样走这条链路（新圆心 → aeqd → 转回工程 CRS），**单一代码路径、无需按 CRS 分支**，
  恒定精确；开销 2.74 ms/个。
- 工程 CRS 无效或未设 → 回退 **EPSG:4326**（`QgsProject.instance().crs()` 无效时）。

## 3. 跨平台（macOS / Windows）

| 维度 | 结论 |
| --- | --- |
| 代码形态 | 纯 Python + Qt，**无编译产物**，同一份源码三平台通用 |
| Qt 版本兼容 | 一律 `from qgis.PyQt import …`（**不要**直接 `import PyQt5`）→ QGIS 4.x 切 Qt6 时代码不用改。已实测 `qgis.PyQt.QtCore/QtGui/QtWidgets` 全部可导入 |
| 图标资源 | **不要用 .qrc 编译**（pyrcc5 / PyQt6 两套产物不通用），直接 `QIcon("图标文件绝对路径")` |
| 配置持久化 | 用 `QgsSettings`（QGIS 封装，跨平台），不用注册表 / plist |
| 路径 | 一律 `os.path.join` / `pathlib`，禁止硬编码 `/` 或 `\` |
| QGIS 版本 | 建议 `qgisMinimumVersion = 3.22`（本次用到的 API 在 3.22 均存在）；实测 3.44.10 无警告 |

**用户侧安装**：QGIS → 插件 → 管理和安装插件 → 从 ZIP 安装，macOS 与 Windows 操作完全一致。

## 6. 风险与待确认（3 项）

### ✅ 风险 1：图源坐标系偏移 —— 已解除（用户确认）

**用户确认：三个图源均为在线 WGS84 图源，无需做偏移校正。**
插件不再内置 GCJ-02 换算开关。

（原测算留档：若将来接入 GCJ-02 图源，WGS84 与其在北京相距 556.1 m、上海 478.5 m、广州 623.7 m、
深圳 606.0 m —— 在 5 km 尺度上相当于约 10% 的定位误差，届时必须加换算。）

### ⚠️ 风险 2：QGIS 原生测量工具已存在

QGIS 自带「测量」工具（线/面积）。我们的价值不在重复它，而在**机场场景化**：
- 一键量两个机位的间距（判断是否需补点）
- 统计全部覆盖圆的总面积、两两重叠面积、未覆盖盲区
- 半径输入框直接改 5 km → 任意值（不同机型覆盖半径不同）

建议做**专用面板**而非替代原生工具。

### ⚠️ 风险 3：Qt5/Qt6 过渡

QGIS 3.x 用 Qt5，QGIS 4.x 将切 Qt6。用 `qgis.PyQt` 抽象层 + 不编译 `.qrc` 即可规避（见 §3）。

## 7. 剩余待确认（按重要性排序）

| # | 问题 | 我的建议 |
| --- | --- | --- |
| 1 | **工程 CRS 是 3857 时的显示观感** | 5 km 圆存进 3857 后，在墨卡托上会显示成**南北向拉长的椭圆**（所有等距圆都如此，非缺陷），但会影响"覆盖区"的直观判断。**建议工程 CRS 用 EPSG:4326 或当地高斯/UTM 带**，插件在检测到 3857 时给一次提示 |
| 2 | **加底图会不会改掉工程 CRS** | QGIS 添加首个图层（3857 底图）时可能弹窗/自动改工程 CRS。插件加底图时**只加图层、不调 `setCrs()`**，并在加完后再写回原工程 CRS |
| 3 | **图层存哪儿** | memory 图层关闭即丢。建议**直接建 GeoPackage 图层**（工程同目录 `机位覆盖.gpkg`），或 memory + 面板上「导出机位方案」按钮。**需要你选** |
| 4 | **半径是否可调** | 默认 5 km（大疆机场实测值）。不同机型覆盖半径不同，**建议半径可输入**，并在属性里留 `radius_m` 字段 |
| 5 | **用户用 QGIS 原生工具挪圆后半径会失真** | 尤其在 4326 / 3857 工程下。建议面板加一个「**按 5 km 重算所选圆**」按钮兜底（也可监听 `geometryChanged` 自动重算，但会与用户手动改半径冲突，故倾向手动按钮） |
| 6 | **要不要多机位统计** | 总面积 / 两两重叠 / 盲区。QGIS 的 Processing 工具箱本身能做（union/intersect/difference），插件里做常用的一键统计即可 |
| 7 | **椭球跟随** | 测量用 `QgsProject.instance().ellipsoid()` 跟随工程椭球（CGCS2000 用 GRS80），而不是硬编码 WGS84；两者差异 < 1 mm，但跟随更规范 |
